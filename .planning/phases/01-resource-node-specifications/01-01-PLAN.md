    **00-lifecycle-archetypes.md** -- Create shared archetype definitions document:

    Define four lifecycle archetypes (per Claude's discretion from CONTEXT.md):

    1. **Simple CRUD** archetype:
       - State machine: (none) -> draft -> deploying -> deployed -> updating -> failed -> destroying -> destroyed (per D-03)
       - Applies to: service_account, secret_manager, gcs_bucket, pubsub_schema, pubsub_topic, pubsub_subscription, cloud_task_queue, bigquery, bigtable
       - Behavior: Create via TF apply, update mutable fields in-place, immutable field changes trigger destroy-recreate, delete via TF destroy
       - Failure states per D-04: Mark failure as possible on deploying->failed, updating->failed, destroying->failed. Note "recovery deferred to Phase 3-5"

    2. **Compute with Image** archetype:
       - Same state machine as Simple CRUD
       - Applies to: cloud_run, cloud_run_job, cloud_function
       - Key difference: Container image / source code changes create new revisions/versions WITHOUT destroying the resource. Template/config changes also create new revisions.
       - Note: "update (immutable)" transition only applies to true ForceNew fields (name, location), NOT to image/source changes

    3. **Parent-Child Composite** archetype:
       - Parent has same state machine as Simple CRUD
       - Child types have coupled lifecycle: deleting parent cascades to children
       - Applies to: cloud_sql (children: cloud_sql_database, cloud_sql_table), firestore (children: firestore_collection), bigquery (children: bigquery_table)
       - Note which children have independent TF resources (cloud_sql_database -> google_sql_database, bigquery_table -> google_bigquery_table) vs platform-only (firestore_collection, cloud_sql_table)

    4. **Network with Dependencies** archetype:
       - Same state machine as Simple CRUD
       - Applies to: vpc, subnet, vpc_connector, external_lb
       - Key difference: Other resources depend on these; deletion requires checking for dependents first
       - Special case: vpc_connector is ENTIRELY immutable (all fields ForceNew) -- any change = full recreation

    5. **Non-Terraform (platform-only)** special case:
       - Simplified state machine: (none) -> active -> deleted (Firestore CRUD only, no TF states)
       - Applies to: third_party_api
       - All fields always mutable (D-09: platform-metadata fields)

    Include the full state machine table (per D-03) with these states and transitions:
    | Current State | Event | Next State | Notes |
    - (none) -> create -> draft
    - draft -> deploy -> deploying
    - deploying -> success -> deployed
    - deploying -> failure -> failed
    - deployed -> update (mutable) -> updating

    - deployed -> delete -> destroying
    - destroying -> success -> destroyed

    **security/02-security-patterns.md** -- Narrative:
    - IAM scope difference: service_account has no iam_scope in REGISTRY (it IS the identity, not a target), secret_manager has iam_scope="resource" with google_secret_manager_secret_iam_member
    - service_account roles field: platform-level IAM metadata that tracks which GCP roles this SA should have -- NOT a Terraform field. IAM binding generation deferred to Phase 6.
    - secret_manager value lifecycle: the `value` field is platform-only (stored in Firestore or set via Secret Manager API), not in Terraform. TF manages the secret resource, not its versions.
    - Deletion protection: secret_manager can have versions that must be destroyed before the secret itself can be deleted
    - These are foundational types: service_accounts are referenced by compute types (service_account field), secrets are referenced by volume mounts and env vars

    **security/03-service-account.md** -- Specifics:
    - Very simple type: 4 fields only
    - account_id generates the SA email: {account_id}@{project}.iam.gserviceaccount.com
    - Naming constraint: account_id must be 6-30 chars, lowercase + hyphens, must start with letter
    - The `roles` field (list of IamRole) is purely platform metadata -- it tracks INTENDED role bindings. Actual IAM binding TF generation is Phase 6.
    - Key integration point: every compute type has a service_account field that should reference a service_account node's account_id

    **security/04-secret-manager.md** -- Specifics:
    - Dual lifecycle: TF manages the Secret resource, platform manages secret versions (values)
    - `replication` is the critical ForceNew field -- choosing automatic vs user_managed replication is permanent
    - The value/value_provided/pending_email fields are a platform UX flow: user can mark a secret as "value needed" and assign someone to provide it via email
    - Version management: each secret can have multiple versions, but the platform currently tracks only current value
    - Integration points: Cloud Run volumes can mount secrets, env vars can reference secrets

    **external/01-external-template.md** -- Rigid template for third_party_api:
    - Terraform Resource: NONE (terraform_resource="" in REGISTRY) -- document this clearly per the "Non-Terraform" archetype

    - No ForceNew fields (no TF resource)
    - No required fields at error severity

    **external/02-external-patterns.md** -- Narrative:
    - third_party_api is the only type with no Terraform resource -- it exists purely as a graph node for dependency tracking
    - Purpose: represents external APIs that the user's services call. Allows the graph to show outbound dependencies.
    - The api_key_secret field can reference a secret_manager node to track where the API key is stored
    - No deploy implications -- this node type is skipped entirely during TF generation
    - Integration: compute nodes can have Invoke edges to third_party_api nodes (from ACTION_VALID_TARGETS)

    **external/03-third-party-api.md** -- Specifics:

    - headers field: default headers to include -- informational for code generation
    - No validation constraints beyond basic type checking (all fields optional)
    - This type may gain more significance in future phases when AI agents use it for code generation context
