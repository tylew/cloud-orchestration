    **data/03-cloud-sql.md** -- Cloud SQL specifics (per D-06: includes cloud_sql_database + cloud_sql_table):

    Cloud SQL instance:
    - Most complex data type: 12 fields + 6 nested sub-models (IpConfiguration, BackupConfiguration, Database, Flag, etc.)
    - database_version is the critical ForceNew field -- changing from POSTGRES_15 to POSTGRES_16 requires destroy-recreate of the ENTIRE instance (data loss without migration)
    - private_network is semi-immutable: you can ADD a private network connection but cannot remove it once set
    - disk_size changes may trigger recreation -- document this as a known gotcha with lifecycle.ignore_changes workaround
    - tier field (machine type like db-f1-micro, db-custom-2-8192) is mutable -- can scale up/down without recreation
    - IP configuration: controls public IP, private IP, authorized networks, SSL enforcement
    - Backup configuration: automated backups, binary log, point-in-time recovery

    Cloud SQL Database (child, per D-06):
    - TF resource: google_sql_database
    - Fields: name (ForceNew -- database name), charset, collation, instance (references parent)
    - Lifecycle coupled to parent: deleting the instance deletes all databases
    - Can be independently created/deleted via TF while instance exists

    Cloud SQL Table (child, per D-06):
    - NO TF resource -- platform-only metadata for schema documentation
    - Fields: table_name, columns (list of column definitions), indexes, constraints
    - Purpose: allows users to define table schemas in the blueprint for documentation and future code generation
    - All fields always mutable (D-09)
    - This is the deepest nesting: cloud_sql -> cloud_sql_database -> cloud_sql_table

    **data/04-firestore.md** -- Firestore specifics (per D-05: includes firestore_collection):

    Firestore database:
    - `type` field (FIRESTORE_NATIVE vs DATASTORE_MODE) is ForceNew and is the most critical choice -- affects query capabilities and data model
    - `location_id` is ForceNew -- cannot move a Firestore database after creation
    - `database_id` defaults to "(default)" -- GCP allows multiple named databases per project
    - `concurrency_mode` (OPTIMISTIC/PESSIMISTIC/OPTIMISTIC_WITH_ENTITY_GROUPS) is mutable
    - `delete_protection_state` must be disabled before database can be deleted
    - `point_in_time_recovery_enablement` is mutable (can enable/disable)

    Firestore Collection (child, per D-05):
    - NO TF resource -- platform-only metadata
    - Fields: collection_name, fields (list of field definitions with name/type), indexes (list of index definitions)
    - Purpose: documents the intended collection schema. Firestore is schemaless but the platform tracks expected structure.
    - Index definitions: field paths + order (ASCENDING/DESCENDING) + composite index support
    - All fields always mutable (D-09)

    **data/05-bigquery.md** -- BigQuery specifics (per D-05: includes bigquery_table):

    BigQuery dataset:
    - `location` is the only ForceNew field -- cannot move a dataset after creation
    - `dataset_id` is surprisingly mutable according to TF docs (but identity-like in practice -- document this nuance)
    - Default table/partition expiration settings are mutable and apply to new tables
    - Access control can be managed at dataset level or delegated to IAM
    - `labels` are mutable and useful for cost attribution

    BigQuery Table (child, per D-05):
    - TF resource: google_bigquery_table
    - Fields: table_id, schema (JSON column definitions), partitioning config (time/range), clustering fields, description
    - Partitioning is a key design choice: time_partitioning (by day/hour/month/year) or range_partitioning
    - Schema changes: adding columns is safe, removing/renaming columns is destructive
    - Lifecycle: can be independently managed via TF, but deletion of parent dataset cascades

    **data/06-bigtable.md** -- Bigtable specifics:

    - Cluster-level immutability: storage_type (HDD/SSD), zone, kms_key_name are ForceNew PER CLUSTER
    - A single Bigtable instance can have multiple clusters (for replication)
    - Autoscaling config is mutable: min_nodes, max_nodes, cpu_target, storage_target
    - deletion_protection is mutable and should be enabled for production instances
    - Instance types: PRODUCTION (3+ nodes) vs DEVELOPMENT (single node, no SLA, no replication)
    - Tables are defined within the instance but use separate TF resource (google_bigtable_table) -- note this is NOT modeled as a child type in the platform currently
    - Column families are the schema unit in Bigtable (not columns) -- GC policies per column family

    **data/07-gcs-bucket.md** -- GCS Bucket specifics:

    - `name` and `location` are identity fields (implicit ForceNew) -- bucket names are globally unique
    - `hierarchical_namespace` and `custom_placement_config.data_locations` are explicit ForceNew
    - `storage_class` is mutable (STANDARD, NEARLINE, COLDLINE, ARCHIVE) -- class transitions have cost implications
    - Lifecycle rules: auto-delete, auto-archive based on age, creation date, custom time, number of versions
    - Versioning: when enabled, preserves old versions of objects -- important for audit trails
    - CORS configuration: needed when buckets serve web content or are accessed from browsers
    - `uniform_bucket_level_access`: when enabled, disables ACLs in favor of IAM-only access control (recommended)
    - `force_destroy` behavior: by default, non-empty buckets cannot be deleted. Platform must handle this.
    - Integration points: Cloud Functions can trigger on bucket events, Cloud Run can mount buckets as volumes
