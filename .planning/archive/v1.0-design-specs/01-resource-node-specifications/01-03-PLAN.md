    - Pub/Sub trilogy relationship: schema defines message format, topic is the channel, subscription is the consumer endpoint. Schema -> Topic -> Subscription is the dependency chain.
    - Ordering dependencies: schema must exist before topic references it (schema_settings.schema), topic must exist before subscription references it
    - Cloud Tasks vs Pub/Sub: Tasks are for targeted HTTP/App Engine invocation with rate limiting; Pub/Sub is for fan-out messaging. Different use cases but same category.
    - IAM scope: pubsub_topic, pubsub_subscription, cloud_task_queue all have resource-level IAM (iam_scope="resource"). pubsub_schema has no IAM scope.
    - Action types: Emit action targets pubsub_topic; Enqueue action targets cloud_task_queue (from ACTION_VALID_TARGETS in enums.py)
    - Subscription delivery types: push (HTTP endpoint), pull (client polls), BigQuery export, Cloud Storage export -- determined by which config is set
    - Dead letter topics: subscription can route failed messages to another topic -- creates an implicit dependency edge

    **network/02-network-patterns.md** -- Narrative covering:
    - Dependency ordering: VPC must exist before Subnet, Subnet before VPC Connector. This is the natural deployment order and critical for Phase 3 (Deploy Sequencing).
    - "Network with Dependencies" archetype behavior: these resources are infrastructure layers. Deleting a VPC requires first deleting all subnets, connectors, and resources that reference it.
    - VPC Connector total immutability: the one resource where ANY change = full recreation. The platform must warn users that changing VPC Connector config will cause downtime for connected Cloud Run services.
    - External LB composite nature: unlike all other types that map 1:1 to TF resources, External LB is a composite of global_address + managed_ssl_certificate + backend_service + url_map + target_https_proxy + forwarding_rule + serverless_neg + optional CDN policy. Each sub-resource has its own lifecycle.
    - CIDR management: subnets require non-overlapping CIDR ranges within a VPC. VPC Connectors also consume a /28 CIDR. This is critical for Phase 7 (Networking Architecture).
    - ip_cidr_range expansion: subnet CIDR can be expanded but NEVER shrunk -- document this one-way mutability clearly
    - No IAM scope: vpc, subnet, vpc_connector have no iam_scope in REGISTRY. external_lb also has no iam_scope. Network resources are accessed via network configuration, not IAM bindings.

    **network/03-vpc.md** -- Specifics:
    - `auto_create_subnetworks`: when true, GCP auto-creates one subnet per region. Platform should recommend false (custom mode) for explicit CIDR control.
    - `routing_mode`: REGIONAL (default) routes within region only; GLOBAL routes across all regions. Mutable.
    - `mtu`: Maximum Transmission Unit (1460 default, up to 8896). Mutable but changing affects all connected resources.
    - `delete_default_routes_on_create`: ForceNew. When true, removes the default 0.0.0.0/0 route. Needed for custom routing tables.
    - `description`: Surprisingly ForceNew -- changing VPC description requires recreation. Document this as a gotcha.
    - VPC is the root network resource: everything else (subnet, connector, Cloud SQL private IP, etc.) references back to VPC.

    **network/04-subnet.md** -- Specifics:
    - `ip_cidr_range`: Required, must be a valid CIDR. CAN be expanded (e.g., /24 to /20) but CANNOT be shrunk. This is a one-way mutable field -- unique behavior.
    - `private_ip_google_access`: Enables private access to Google APIs without public IP. Critical for Cloud SQL private networking.
    - `secondary_ip_ranges`: Used for GKE pod/service ranges. Each secondary range has its own CIDR.
    - `log_config`: VPC Flow Logs configuration (aggregation_interval, flow_sampling, metadata). Mutable.
    - `network` reference: must reference a VPC node. This creates a hard dependency in the blueprint graph.
    - `region`: ForceNew -- subnets are regional resources, cannot move between regions.

    **network/05-vpc-connector.md** -- Specifics:
    - **ENTIRELY IMMUTABLE** (Pitfall 3): ALL fields are ForceNew. Any change = destroy + recreate.
    - `machine_type`: e2-micro (default), e2-standard-4, f1-micro. Determines throughput capacity. CANNOT be changed after creation.
    - `min_instances` / `max_instances`: Scaling bounds. CANNOT be changed after creation. Must be chosen carefully upfront.
    - `min_throughput` / `max_throughput`: Alternative to min/max_instances for throughput-based scaling. CANNOT be changed.
    - `ip_cidr_range` or `subnet`: Two mutually exclusive ways to specify the network. ip_cidr_range auto-creates a /28, subnet references an existing subnet.
    - Connector consumes a /28 CIDR block from the VPC's address space.
    - Impact on dependents: Cloud Run services reference VPC Connector by name. Recreating a connector breaks ALL connected Cloud Run services until they are redeployed with the new connector.
    - Platform UX implication: must show a strong warning when any VPC Connector field is modified. This is the only resource type where the entire config is immutable.
    - Consider documenting Cloud Run Direct VPC Egress as a future alternative that avoids connectors entirely (mentioned in RESEARCH.md State of the Art).

    **network/06-external-lb.md** -- Specifics (Pitfall 5 -- composite resource):
    - COMPOSITE RESOURCE: The platform's ExternalLbConfig maps to MULTIPLE Terraform resources. Document each:

      2. `google_compute_managed_ssl_certificate` -- SSL cert for domain (ForceNew: domains)

      6. `google_compute_global_forwarding_rule` -- Binds IP + port to proxy (ForceNew: ip_address, port_range)
      7. `google_compute_region_network_endpoint_group` -- Serverless NEG pointing to Cloud Run (ForceNew: network_endpoint_type, region)
      8. `google_compute_backend_service` CDN policy (optional, mutable)

    - ExternalLbConfig fields (13 fields + 6 nested sub-models): domains, ssl_policy, backends (list of Backend with Cloud Run service + weight), cdn_policy, iap_config, security_policy, custom_headers, health_check, connection_draining_timeout, logging, etc.

    - This type has the most complex lifecycle of any node type. Downstream phases must handle each sub-resource independently.
